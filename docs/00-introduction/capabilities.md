# 网关核心能力清单

网关最容易犯的错，不是少做一个功能，而是**一次做太多**。这一篇给你一张能力地图，按阶段取用。

## 四级能力模型

| 等级 | 名称 | 关键词 | 典型能力 |
| --- | --- | --- | --- |
| L0 | 透明代理 | 能通 | 请求转发、密钥托管、request id、健康检查 |
| L1 | 可运营 | 不失控 | 鉴权、超时、错误归一、限流、结构化日志 |
| L2 | 可治理 | 可调度 | 路由、兜底、缓存、成本归因、Trace、指标 |
| L3 | 平台化 | 可经营 | 多租户、账单、灰度、审计、自助开通 |

多数团队应该先做到 **L1 完整 + L2 的关键两项**（路由与可观测），再谈 L3。跳级的代价通常是：功能有了，但数据不准、故障定位不了、没人敢用。

## 能力地图

### 接入与协议

- [ ] OpenAI Chat Completions 兼容入口
- [ ] 流式（SSE）与非流式都支持
- [ ] 至少两家厂商的适配器
- [ ] 工具调用（tools / tool_calls）字段映射
- [ ] 请求校验：`messages`、`model`、`max_tokens` 边界
- [ ] 模型别名（客户端不直接依赖厂商模型名）

### 治理与安全

- [ ] 网关密钥签发、轮换、吊销
- [ ] 租户 / 项目 / 密钥三级身份
- [ ] 模型白名单与路由标签权限
- [ ] RPM、TPM、并发、日/月预算
- [ ] 请求体大小、消息数、最大 token 限制
- [ ] 日志脱敏，密钥与 prompt 默认不落盘

### 可靠性

- [ ] 连接 / 首 Token / 空闲 / 总时长四类超时
- [ ] 可重试错误判定与指数退避
- [ ] 熔断与半开探测
- [ ] 兜底模型链（能力对齐，不盲目降级）
- [ ] 优雅停机与流式连接排空
- [ ] 健康检查区分 liveness / readiness

### 成本与缓存

- [ ] 从 usage 字段精确计量
- [ ] 流式 usage 缺失时的估算兜底
- [ ] 按租户 / 项目 / 模型 / 功能归因
- [ ] 预算预警与硬停策略
- [ ] 精确缓存与缓存失效
- [ ] Prompt / KV Cache 命中统计

### 可观测

- [ ] 结构化 JSON 日志 + request id
- [ ] W3C Trace 上下文传播
- [ ] TTFT、总延迟、错误率、重试率指标
- [ ] 缓存命中率、token 消耗、单位成本
- [ ] 按 target 的上游健康指标
- [ ] 告警规则与值班手册

### 运维

- [ ] 无状态部署与水平扩展
- [ ] 配置热更新与回滚
- [ ] 密钥与配置分离（Secret Manager）
- [ ] 灰度 / 金丝雀发布
- [ ] 容量模型与压测基线
- [ ] 备份与灾难恢复

## 最小上线集（MVP）

如果你只做第一版，做这 10 件事就够了：

1. **OpenAI 兼容入口** + 流式透传。
2. **request id** 贯穿日志、响应头、上游请求。
3. **真实密钥收口**，客户端只拿网关密钥。
4. **四类超时**，尤其是首 Token 超时。
5. **错误归一**：上游错误映射成稳定错误码。
6. **基础配额**：每密钥 RPM + 日预算。
7. **一个备用模型** + 可配置兜底链。
8. **结构化日志**，默认不记录 prompt。
9. **TTFT / 错误率 / token 用量** 三个指标。
10. **健康检查 + 多副本**。

这 10 件事做完，网关才配叫「生产入口」，而不是「多一层代理」。

## 90 天落地路线

| 时间 | 目标 | 交付物 |
| --- | --- | --- |
| 第 1～2 周 | 跑通 | 最小网关、两家模型、流式、request id |
| 第 3～4 周 | 可控 | 鉴权、密钥生命周期、基础限流、错误码 |
| 第 5～6 周 | 可观测 | JSON 日志、Trace、TTFT/错误率看板 |
| 第 7～8 周 | 可调度 | 模型别名、权重路由、兜底链、熔断 |
| 第 9～10 周 | 算清账 | usage 计量、租户归因、预算告警 |
| 第 11～12 周 | 可演练 | 压测、故障注入、灰度、值班手册 |

这张表假设 1～2 名工程师投入。人更少就拉长，不要压缩「可观测」和「演练」——它们是后面所有能力的验收标准。

## 自评打分表

选型或验收时，可以按权重打分（1～5 分）：

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 协议兼容 | 20% | SDK 能否零改动接入 |
| 稳定性 | 20% | 超时、重试、熔断、流式错误处理 |
| 租户与配额 | 15% | 层级、继承、超限行为 |
| 成本与账单 | 15% | usage 精度、归因维度、预算 |
| 可观测 | 15% | Trace、指标、日志、告警 |
| 扩展性 | 10% | 二次开发、配置热更新 |
| 运维成本 | 5% | 部署、升级、值班 |

::: tip 打分的原则
先给「一票否决项」划红线，再算总分。比如「必须支持按租户拆分账单」不满足，其他项再高也不选。
:::

## 常见反模式

::: danger 只做协议转换
请求能转发，但超时、配额、计量都没有。上线后所有问题仍然由业务系统各自处理。
:::

::: danger 配额只放内存
单机计数看起来没问题，一扩副本就失效；重启即清零，用户可以在发布窗口「白嫖」额度。
:::

::: danger 把 prompt 打进日志
调试很方便，泄露很彻底。默认脱敏、按需采样、设置保留期，是底线。
:::

::: danger 兜底模型不做能力对齐
主模型支持工具调用，备用模型不支持，切过去后 Agent 直接崩。兜底链要按能力标签匹配。
:::

::: danger 没有 request id
上游说 500，网关说 502，业务说超时，三边对不上。一个贯穿的 request id 能省掉一半排障时间。
:::

## 验收清单

上线前，用下面五个问题验收：

- [ ] 随便挑一条失败请求，能否在 5 分钟内定位到「哪个租户、哪个目标、哪类错误」？
- [ ] 关掉主模型，系统是否按预期切到备用模型，并留下清晰日志？
- [ ] 某个租户突然打满配额，是否只影响他自己？
- [ ] 账单能否按租户拆开，并与厂商账单对上量级？
- [ ] 网关发布新版本时，流式请求能否优雅排空？

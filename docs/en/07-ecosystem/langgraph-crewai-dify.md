# LangGraph / CrewAI / Dify Integration

These three frameworks cover most upper-layer scenarios: LangGraph for controllable graph orchestration, CrewAI for role collaboration, and Dify for low-code applications. All of them support OpenAI-compatible APIs, so connecting them to a self-built gateway works the same way: **change `base_url` and `api_key`, then line up the model name**.

The hard part is that each framework resolves "model names" differently, and their implementations of tool calling, streaming, and usage reporting are not consistent.

## The bottom line

- **Everything goes through the OpenAI-compatible endpoint**; do not let frameworks talk to vendor SDKs directly.
- **Separate the "framework prefix" from the "gateway alias"**: in `openai/xxx`, `xxx` is the model the gateway sees.
- **Tool calling is the biggest compatibility point**; schemas generated by frameworks may contain fields your upstream does not support.
- **Verify streaming down to the last chunk**, including usage and `[DONE]`.
- **Attribution relies on headers**; most frameworks let you set custom headers to pass `run_id`/`tenant` through.

## Common integration checklist

| Item | Configuration |
| --- | --- |
| Base URL | `https://gateway.example.com/v1` |
| API Key | Tenant key issued by the gateway |
| Model name | The gateway alias, such as `chat-default` |
| Streaming | Confirm it is enabled in both the framework and the gateway |
| Tool calling | Confirm the target model supports it and schemas are compatible |
| Timeout | Longer than the longest streaming duration |
| Retries | Disable or set to 0 on the framework side |
| Headers | `X-Run-Id`, `X-Feature`, and similar |

::: warning The `/v1` in base_url
The OpenAI SDK appends `/chat/completions` to `base_url`. If you write `https://gateway.example.com`, the actual request becomes `https://gateway.example.com/chat/completions`, missing `/v1`. Always write `https://gateway.example.com/v1`.
:::

## LangGraph

LangGraph itself is not tied to a model; models come from LangChain chat models. Connecting to the gateway means configuring `ChatOpenAI`:

```python
import os

from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, MessagesState, START, END


def make_model(step: str) -> ChatOpenAI:
    return ChatOpenAI(
        model="chat-default",
        base_url="https://gateway.example.com/v1",
        api_key=os.environ["LGW_API_KEY"],
        timeout=120,
        max_retries=0,
        default_headers={
            "X-Feature": "langgraph-demo",
            "X-Step-Type": step,
        },
        stream_usage=True,
    )
```

`max_retries=0` matters: let the gateway handle upstream retries so the two layers do not stack.

### Different models per node

```python
planner = make_model("plan")
executor = make_model("act")


def plan_node(state: MessagesState):
    resp = planner.invoke([
        {"role": "system", "content": "Break the task into steps and output JSON."},
        *state["messages"],
    ])
    return {"messages": [resp]}


def act_node(state: MessagesState):
    resp = executor.invoke(state["messages"])
    return {"messages": [resp]}


builder = StateGraph(MessagesState)
builder.add_node("plan", plan_node)
builder.add_node("act", act_node)
builder.add_edge(START, "plan")
builder.add_edge("plan", "act")
builder.add_edge("act", END)
graph = builder.compile()
```

If you want the gateway to decide which model to use, pass `model="agent-default"` everywhere and route on `X-Step-Type`. Either approach works; **the key is not to hard-code a specific provider in the framework**.

### Streaming

```python
async for event in graph.astream_events(
    {"messages": [{"role": "user", "content": "Research vector databases"}]},
    version="v2",
):
    if event["event"] == "on_chat_model_stream":
        chunk = event["data"]["chunk"]
        if chunk.content:
            print(chunk.content, end="", flush=True)
```

LangGraph's event stream includes output from multiple nodes. The gateway sees several independent model calls, so stitch them together with `run_id` when attributing cost.

### Tool calling

LangChain's `bind_tools` generates JSON Schema. If the upstream has limited schema support, simplify first:

```python
from pydantic import BaseModel, Field


class SearchInput(BaseModel):
    query: str = Field(description="Search keywords; keep them short")
    top_k: int = Field(default=5, ge=1, le=20)


tools = [{
    "type": "function",
    "function": {
        "name": "search",
        "description": "Search the knowledge base",
        "parameters": SearchInput.model_json_schema(),
    },
}]

model_with_tools = executor.bind_tools(tools)
```

Avoid `$ref`, complex `oneOf`, and recursive structures; some providers do not support them.

## CrewAI

CrewAI uses LiteLLM under the hood to parse model names, so the format is `<provider>/<model>`. When connecting to a self-built gateway, set the provider to `openai` and follow it with the gateway alias:

```python
import os

from crewai import Agent, Crew, LLM, Task

gateway = LLM(
    model="openai/chat-default",
    base_url="https://gateway.example.com/v1",
    api_key=os.environ["LGW_API_KEY"],
    temperature=0.3,
    timeout=120,
)

researcher = Agent(
    role="Researcher",
    goal="Find reliable sources and summarize them",
    backstory="You are good at cross-checking information across multiple sources.",
    llm=gateway,
    verbose=True,
)

writer = Agent(
    role="Writer",
    goal="Turn research findings into a clear report",
    backstory="You only use the facts provided by the researcher.",
    llm=gateway,
)

research = Task(
    description="Research common routing strategies for LLM gateways",
    expected_output="A comparison of at least 3 strategies",
    agent=researcher,
)

write = Task(
    description="Write a 500-word report based on the research",
    expected_output="A clearly structured report",
    agent=writer,
)

crew = Crew(agents=[researcher, writer], tasks=[research, write])
result = crew.kickoff()
```

A few pitfalls:

- **`model` must carry the `openai/` prefix**, or LiteLLM may resolve it against another provider.
- **Do not repeat `/v1` in `base_url`**; CrewAI appends it.
- **Tool calling**: CrewAI's tool system generates fairly complex schemas. On a 400, reduce the number of tools or simplify parameters first.
- **Retries**: CrewAI/LiteLLM has its own retries; lower them so they do not stack with the gateway's.

## Dify

Dify connects to a self-built gateway through the "OpenAI-API-compatible" model provider, configured under "Settings → Model Providers":

| Field | Value |
| --- | --- |
| Base URL | `https://gateway.example.com/v1` |
| API Key | Tenant key |
| Model Name | `chat-default` |
| Function Calling | Choose based on model capability |
| Streaming | Enabled |
| Context Size | Fill in according to the model |

If you self-host Dify, you can also preset it with environment variables:

```yaml
# Environment variable snippet for dify-api in docker-compose
OPENAI_API_BASE: https://gateway.example.com/v1
OPENAI_API_KEY: ${LGW_API_KEY}
```

Note that Dify's model configuration UI **usually expects Base URL to end with `/v1`**, while some versions append `/v1` automatically. After configuring, use "Test connection" to verify and avoid `/v1/v1`.

### Two things to watch in Dify

1. **Function Calling capability**: Dify decides whether to enable tool calling based on the model configuration. If the model the gateway actually routes to does not support tools, Agent nodes will fail. Either route by capability on the gateway side, or bind only tool-capable models in Dify.
2. **Usage reporting**: Dify workflows count tokens, but they rely on the usage returned by the upstream. Enable `stream_options.include_usage`, or the counts will be empty.

## Comparison

| Dimension | LangGraph | CrewAI | Dify |
| --- | --- | --- | --- |
| Integration | LangChain ChatModel | LiteLLM style | Model provider plugin |
| Model name | Gateway alias | `openai/<alias>` | Gateway alias |
| Custom headers | Supported | Partially supported | Limited |
| Streaming | Event stream, fine-grained | Supported | Supported |
| Tool calling | Custom schema | Auto-generated, fairly complex | Visual configuration |
| Multi-model routing | Specified in code | Per agent | Per node |
| Best for | Complex, controllable orchestration | Role collaboration | Low-code applications |

## Headers and attribution

The framework's `run_id` must reach the gateway before you can attribute cost per task.

**LangGraph / LangChain**:

```python
model = ChatOpenAI(
    model="chat-default",
    base_url="...",
    api_key="...",
    default_headers={"X-Run-Id": run_id, "X-Feature": "research"},
)
```

**CrewAI**: pass it via `LLM(extra_headers=...)` or a global environment variable. The exact fields vary by version, so it is worth also supporting extraction from the request body's `metadata` on the gateway side.

**Dify**: custom header support is limited; usually you can only set fixed values per application. If you must attribute per request, distinguish applications on the gateway side by key.

## Common failures

| Symptom | Cause | Fix |
| --- | --- | --- |
| 404 | Model name carries a provider prefix the gateway does not recognize | Support aliases on the gateway, or strip the prefix |
| 404 with a path like `/v1/v1/...` | Duplicated base_url | Keep a single `/v1` |
| 400 tool schema | Schema contains unsupported fields | Simplify; remove `$ref`/`oneOf` |
| Tool calls turn into text | Target model does not support tools | Route by capability |
| Streaming interrupts | Proxy buffering or timeout | Check gateway and proxy configuration |
| Empty usage | `include_usage` not enabled | Enable it in the framework or gateway |
| Double billing | Both framework and gateway retry | Set `max_retries=0` on the framework side |
| Slow time to first token | The framework runs other nodes first | Inspect the trace; separate framework time from model time |

## Choosing a framework

- **When you need precise control over every step, conditional branches, and human-in-the-loop**: LangGraph.
- **When you want a multi-role workflow up quickly**: CrewAI.
- **When business users want to build apps with little code**: Dify.
- **All three can coexist**: they are just clients of the gateway, and the gateway needs no special adaptation for any framework.

What really needs to be standardized is: model aliases, header conventions, and billing semantics. Once these three are settled, swapping frameworks on top does not affect the platform.

## Anti-patterns

| Anti-pattern | Consequence |
| --- | --- |
| Each framework connects directly to a different provider | Adapters and billing fragment |
| Model names hard-code provider model IDs | Changing models requires code changes |
| Retries in both framework and gateway | Traffic amplification and double billing |
| base_url missing or duplicating `/v1` | 404 |
| No `run_id` passed | No per-task attribution |
| Ignoring tool schema compatibility | Tool calls fail intermittently |
| Not verifying the last streaming chunk | Usage and finish reason are lost |

## Checklist

- [ ] All three frameworks point to the same gateway endpoint
- [ ] `base_url` consistently ends with `/v1`
- [ ] Model names use gateway aliases, not provider model IDs
- [ ] Framework-side retries disabled or reduced
- [ ] Tool schemas verified on the target model
- [ ] Streaming includes usage and the finish marker
- [ ] `run_id`/`feature` attributed via headers or keys
- [ ] Timeouts cover the longest streaming duration
- [ ] Debugging paths exist for common 404/400 errors
